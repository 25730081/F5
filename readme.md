## 2. 프로젝트 개요

### 1.1 해결하려는 문제

식당에서 웨이팅하는 동안 사용자는 남은 시간을 어떻게 활용할지 결정하기 어렵습니다. 주변에 갈 만한 장소가 있어도 이동 시간과 체류 시간을 계산하기 번거롭고, 식당으로 제시간에 돌아올 수 있을지 판단하기 어렵습니다.

**0차**는 사용자가 식당의 웨이팅 장소와 남은 시간을 입력하면 주변 장소를 지도에서 탐색하고, 남은 시간 안에 다녀올 수 있는 장소를 골라 하나의 코스로 구성하도록 돕습니다.

### 1.2 제품 목표

1. 웨이팅 중 낭비되는 시간을 주변 공간 방문 시간으로 전환합니다.
2. 남은 시간에 맞는 장소를 쉽게 탐색하고 선택할 수 있도록 합니다.
3. 이동·체류 시간을 계산해 식당 복귀 가능 여부를 판단하도록 돕습니다.
4. 코스 진행 상황과 남은 시간을 한눈에 확인하도록 합니다.

### 1.3 핵심 가치

- **시간 활용:** 기다리는 시간을 의미 있는 외출 시간으로 전환
- **간편한 탐색:** 지도와 카테고리로 주변 장소 확인
- **복귀 관리:** 이동·체류 시간을 고려해 복귀 여유 시간 확보
- **코스 관리:** 코스 저장, 수정, 재시작 및 관심 장소 관리

## 3. 사용자 및 사용 시나리오

### 2.1 주요 사용자

- 식당에서 웨이팅 중인 사람
- 대기시간 동안 주변 카페·서점·도서관·공원·쇼핑 공간 등을 방문하고 싶은 사람
- 식당 복귀 시간을 놓치지 않으면서 짧은 외출을 계획하고 싶은 사람

### 2.2 대표 사용자 흐름

1. 사용자가 홈 화면에서 **웨이팅 시간 등록하기**를 선택합니다.
2. 지도에서 현재 웨이팅 중인 식당의 위치를 지정합니다.
3. 남은 웨이팅 시간을 입력합니다.
4. 주변 장소 지도에서 장소를 검색하거나 카테고리별로 탐색합니다.
5. 방문할 장소를 코스에 담습니다.
6. 서비스가 도보 이동시간과 체류시간을 기준으로 코스 소요시간을 계산합니다.
7. 코스를 확인하고 진행을 시작합니다.
8. 진행 화면에서 타임라인과 남은 시간을 확인하고, 필요하면 코스를 수정합니다.
9. 코스를 마친 뒤 식당으로 복귀합니다.

### 3.2 시간 계산 정책

현재 코드에서 확인되는 계산 기준입니다.

- 도보 이동시간은 웨이팅 장소와 각 장소 사이의 직선거리를 바탕으로 추정합니다.
- 거리 추정에는 직선거리 보정값 `1.3`과 도보 속도 `4.8km/h`를 사용합니다.
- 코스 시간은 각 장소의 **왕복 도보 이동시간 + 체류시간**을 합산합니다.
- 코스 복귀 가능 여부를 판단할 때 **10분의 복귀 여유 시간(BUF)**을 확보합니다.
- 기본 체류시간은 10분으로 설정되어 있습니다.
- 웨이팅 시간이 60분 이하인 경우, 기본 체류시간 계산은 0분으로 처리됩니다.
- 코스에 담은 장소별 체류시간은 사용자가 조정할 수 있습니다.

**주의:** 이동시간은 실제 길찾기 경로·교통·보행 속도를 반영한 확정값이 아니라 참고용 추정치입니다. 사용자에게 정확한 복귀 시각을 보장하는 기능으로 설명하지 않습니다.

### 3.4 비기능 요구사항 및 운영 기준

- 모바일 화면을 우선 고려한 반응형 레이아웃을 제공합니다.
- 버튼과 입력 영역은 터치 환경에서 사용하기 쉽도록 구성합니다.
- 장소 데이터가 없거나 좌표가 유효하지 않은 항목은 지도 표시 대상에서 제외합니다.
- 외부 링크는 허용된 웹 주소 형식인지 확인한 뒤 연결합니다.
- 지도 SDK와 외부 길찾기 서비스는 네트워크 및 키 설정에 영향을 받습니다.
- 장소 데이터의 정확성, 최신성, 운영시간은 원본 데이터 제공처에 따라 달라질 수 있습니다.

### 4.3 데이터 파일

| 파일 | 데이터 |
|---|---|
| `seoul_bookstore_100.json` | 서울 지역 서점 정보 |
| `seoul_library_100.json` | 서울 지역 도서관 정보 |
| `seoul_park_130.json` | 서울 지역 공원 정보 |

- 서점·도서관·공원 데이터는 각 JSON 파일을 읽어 장소 목록으로 변환합니다.
- 카페·쇼핑 데이터는 코드에 샘플 데이터 파일 경로가 정의되어 있으나, 이번에 전달된 ZIP에는 해당 파일이 포함되어 있지 않습니다. 따라서 별도 데이터 연결 및 파일 포함 여부를 확인해야 합니다.
- 외부 API 장소를 추가할 수 있도록 `addApiPlaces()` 함수가 정의되어 있습니다.

## 9. 버전 및 문서 관리 규칙

### 8.1 버전 번호

- `v0.1`, `v0.2`처럼 제품 버전을 관리합니다.
- 기능 추가 또는 기존 기능의 의미 있는 변경은 마이너 버전 번호를 올립니다.
- 오탈자, 문구, 작은 스타일 수정처럼 동작에 영향이 적은 변경은 패치 버전 사용을 검토합니다.
- `app.js v8`, `style.css v9` 같은 파일 내부 버전은 제품 버전과 별도로 기록합니다.

### 8.2 변경 이력 작성 형식

새 버전을 배포할 때 아래 형식으로 `변경 이력`에 추가합니다.

```markdown
### v0.5 — YYYY-MM-DD

**추가**
- 새로 추가한 기능

**변경**
- 기존 기능의 변경 사항

**수정**
- 해결한 오류 및 문제

**제외 / 보류**
- 제거하거나 다음 버전으로 미룬 기능
```

### 8.3 PRD 업데이트 원칙

- 실제 구현된 기능과 앞으로 구현할 기능을 구분합니다.
- 요구사항이 바뀌면 기능 요구사항 표와 화면 흐름을 함께 수정합니다.
- 구현 여부가 확인되지 않은 기능은 완료로 표시하지 않습니다.
- 데이터 출처, 외부 API, 계산 정책이 바뀌면 기술 구성 및 운영 기준도 함께 갱신합니다.
- 각 버전의 변경 사항은 해당 버전의 실제 코드 또는 커밋을 근거로 작성합니다.

## 10. 확인 및 실행

1. 프로젝트 폴더에서 `index.html`을 브라우저로 엽니다.
2. JSON 데이터 파일이 `data/` 경로에 있는지 확인합니다.
3. 지도 기능이 동작하지 않으면 지도 SDK 로딩과 JavaScript 키 설정을 확인합니다.
4. 브라우저 개발자 도구의 Console 및 Network 탭에서 파일 로딩 오류를 확인합니다.

> 브라우저의 보안 정책이나 `fetch()` 사용 환경에 따라 로컬 파일을 직접 여는 방식에서 JSON 로딩이 제한될 수 있습니다. 이 경우 프로젝트 폴더를 로컬 웹 서버로 실행해야 합니다.
